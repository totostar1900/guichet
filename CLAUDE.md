# Guichet — notes pour Claude Code

- Lire README.md pour l'architecture. Langue de l'UI : français ; code et commentaires : anglais court, français pour les libellés métier.
- `src/lib/finance.ts` est la référence pour tout calcul ; ne pas recalculer ailleurs. Tests : `npm test`.
- Les offres sont en lecture seule côté client ; seul le desk fixe prix / ticket minimum (voir `publishOffer`). Le client ne lit que les **frais qu'il couvre**, sous le seul mot « Frais », jamais « commission » ni qui les perçoit (ce que la maison reçoit d'un partenaire ou d'un émetteur ne sort pas du desk) ; barème : `src/lib/domain/frais.ts`, desk › Frais, une date de départ par règle, préavis de 30 jours. **Règle : pour toute transaction (estimation, récapitulatif, avis, annexe), le client lit UNE ligne, les frais totaux à payer ; jamais leur destination ni leur décomposition** (sur un fonds, `src/lib/domain/frais-fonds.ts` additionne les droits du fonds et la règle de la maison ; gardé par `src/test/frais.test.ts`). `positionFor` lit le barème (les cinq règles) par l'instantané de `src/lib/frais-registre.ts`, posé par `loadRegistry()` et envoyé au navigateur par le layout : tout calcul d'ordre côté serveur passe donc par `await loadRegistry()` d'abord.
- Types de produits, échéanciers, glossaire, sociétés, émetteurs : valeurs par défaut en code, surchargées par la table `reference` (desk › Référentiel). Le domaine lit `src/lib/registry.ts` (synchrone) ; toute entrée serveur hors rendu de page appelle `await loadRegistry()` d’abord.
- Le modèle de données vit dans `src/lib/domain/types.ts` ET `supabase/migrations/*.sql` — modifier les deux ensemble, régénérer `supabase/seed.sql` avec `npm run seed:sql`.
- Sans `.env.local`, le repository mémoire est utilisé (données de `src/data/seed.ts`).
- Toute écriture métier passe par `audit()` (src/lib/audit.ts) avec avant / après ; les écritures d'offres passent `expectedVersion` ; les termes financiers passent par `approvalReason()` (src/lib/policy.ts) avant d'écrire.
- Toucher une page de `src/data/docs/*.ts`, c'est porter son `checkedOn` au jour même, **dans le même commit** ; `docs-exactes` lit l'arbre et le refuse avant le commit. Même règle pour un changement d'écran qui rend une page de documentation inexacte : la relire et la dater avec le code.
- L'espace d'une page : six jetons dans `globals.css` (`--sections-gap` 28, `--tuiles-gap`, `--titre-gap`, `--retour-gap`, `--chapitres-gap` 44, `--bloc-gap` 20 entre deux blocs d'une carte ; le texte d'un graphe : `--graphe-texte` 10 px, boîte `GRAPHE_L` × `GRAPHE_H`, ETALON § 8.14, pour l'Accueil et les sections de la fiche d'une ligne) et les classes `pile` / `chapitres` ; jamais un écart en dur ni de marge entre deux blocs d'une page. Règles et migration : `ETALON.md` § 8 ; une page convertie entre dans `src/test/espace-registre.ts`.
- Skills du projet (`.claude/skills/`) : `guichet-maquette` (discuter et maquetter avant de coder), `guichet-espace-tuiles` (écarts, chapitres, tuiles), `guichet-benchmark` (se mesurer à la concurrence à partir d'images de référence), `guichet-bamboo` (tout ce qu'on sait de Bamboo, le modèle cité par le client : journal de ses mentions, principes retenus ou écartés, décisions, travail en attente). Images de référence du design : `docs/design-refs/` (convention dans son README).
- **Les skills se consultent à chaque amélioration et à chaque développement d'écran, pas une fois.** Une demande de conception ou de refonte ouvre `guichet-maquette` ; dès qu'on se compare à d'autres applications ou qu'on juge une hiérarchie, `guichet-benchmark` ; dès que le client cite Bamboo, `guichet-bamboo` (et on y ajoute une ligne au journal) ; dès qu'on touche un écart, un chapitre ou une tuile, `guichet-espace-tuiles` ; un texte de risque ou de mise en garde suit `ETALON.md` § 10 (rassurer sans rien retirer). **Le compte rendu final nomme les skills utilisés** et dit ce qu'on en a appliqué ; une leçon nouvelle s'écrit dans le skill concerné, pas seulement dans la conversation. Gardé par `src/test/skills.test.ts`.
- Avant de conclure : `npm run typecheck && npm run lint && npm test`.
